## Operational note

Mid-session, a `docker compose down` was run without an explicit `-p`/`COMPOSE_PROJECT_NAME`
after a manual (non-wrapper) E2E debugging session, which — because the env var set in a prior
Bash call does not persist across separate tool calls — targeted the main dev stack
(project "astroaxe") instead of the intended isolated "astroaxe_e2e" one. Caught immediately via
`docker ps -a`; no volumes were removed (`down` without `-v`), so no data was lost. The main stack
was brought back up (`docker compose -f compose.yml -f compose.dev.yml up -d --wait`) and verified
healthy with all prior data intact (guest_sessions=10, birth_profiles=13, matching pre-incident
counts) before continuing.
